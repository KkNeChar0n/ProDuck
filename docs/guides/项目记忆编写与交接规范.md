# 项目记忆编写与交接规范

适用项目：证书自动化 SaaS（也可复用于其他产品项目）  
接收方：长期管理该项目、掌握历史资料的 Agent  
使用方：Produck 与后续接手的产品 Agent  
规范日期：2026-11-23

## 1. 你的任务

请阅读本规范，再基于你已经掌握且获准访问的项目资料，输出可供其他 Agent 接手工作的项目记忆。目标是让接手者知道产品服务谁、现有系统如何工作、哪些规则已经验证、当前版本准备改变什么，以及遇到疑问应查哪里。

交付应以产品事实和决策为中心，不要写成聊天流水账、代码文件清单或未经核实的完整 PRD。不要仅凭本规范中的举例推导实际功能；举例和模板不是该项目的真实需求。

先盘点现有材料并完成可以确认的内容。缺失信息写入待确认清单，给出下一步核实方式；仅对会改变关键结论的问题集中询问用户。不能访问的链接明确标记“未读取”，不要据标题补写正文。

本次任务是整理并输出交接文件，不包括修改线上文档、更新云效状态或调整系统配置。

## 2. 必须遵守的事实标准

每条重要业务规则、版本结论和操作限制至少包含：

- **结论**：一条具体、可核对的陈述，避免“完整支持”“智能处理”等空泛表述。
- **依据状态**：已观察、文档规定、代码实现、用户确认、推断、待验证之一。
- **适用范围**：模块、角色、租户/环境、产品版本；无法确定时写“待确认”。
- **来源**：可定位的文档链接与章节、代码路径与提交、页面 URL 与操作步骤，或用户确认记录。
- **核验时间**：实际读取/观察的日期；不能用本次编写日期冒充核验时间。

不同依据不能互相替代：

| 依据 | 可以说明 | 不能直接说明 |
| --- | --- | --- |
| 实际页面操作 | 此环境、角色和时间下观察到的行为 | 所有权限分支、隐藏规则、生产环境行为 |
| PRD / 设计稿 | 文档规定或设计意图 | 已实现、已上线或已通过验收 |
| 代码 / 自动化测试 | 对应提交中的实现或被测试路径 | 当前线上部署内容及真实平台权限 |
| 云效状态 | 工作项当前标注的推进状态 | 代码已发布、业务效果达标或用户已验收 |
| 用户明确确认 | 被确认的具体规则或决定 | 未提及的细节和其他版本 |
| Agent 历史总结 | 发现线索、补充背景 | 无原始依据的可靠事实 |

“待验证”不是失败。明确不知道什么，比编造完整规则更有价值。保留用户原本的术语，同时在术语表解释含义，避免同一个词被不同模块误用。

## 3. 项目与版本如何划分

### 项目记忆：跨版本共享的背景

记录产品定位、用户角色、业务对象、模块关系、长期有效的规则、系统边界、已验证的工作约定，以及各版本索引。

规则曾随版本变化时，注明生效版本；不要把新版设计无条件写成整个项目的现状。

### 版本交接：某一次迭代的变化

单独记录该版本的目标、范围、基于哪个线上/历史版本、原型与 PRD、拟变更规则、验收情况、未解决问题和交付位置。

用“现状 → 本版计划 → 实施/验收证据”的方式描述变化。明确区分：计划中、开发中、已实现未上线、已上线未验收、已验收。允许状态未知，不要推测上线时间。

项目模型、项目工作空间、云效项目连接属于项目配置；飞书迭代父节点属于版本配置。记忆里只登记非敏感目标标识与用途，不保存认证凭证。

对于当前“证书自动化 SaaS”，本机配置曾记录 V1.5.0；必须核对它是否仍是当前迭代。不要仅凭旧 JSON 将其写成截至今天的最新版本。

## 4. 需要整理的内容

### A. 项目总览与边界

说明产品解决的问题、主要使用者及其目标、产品当前覆盖的范围、不负责的业务，以及依赖的外部系统。给出“理解本项目必须先知道的 5–10 条事实”，每条关联来源。

### B. 用户角色与业务对象

列出角色、业务目标、已核实的访问范围。分别描述核心对象的定义、主键/标识含义、关联关系、生命周期和归属范围。

对证书类产品，可检查是否确实存在证书、域名、申请、部署任务等对象；只有找到证据后才能写入。不要把这些候选对象当成既定模块。

### C. 模块与页面地图

按实际菜单或业务模块组织，列出页面名称、入口、用途、主要操作、关联对象、已观察角色和资料来源。需要登录的页面记录正常入口即可，不记录带登录票据的地址。

### D. 关键业务流程

每条流程至少说明：触发条件 → 前置条件 → 用户操作 → 状态变化 → 结果。补充已知的权限限制、取消、失败、重试、超时、重复提交和空态处理。

把“页面显示成功”“后台任务完成”“外部系统读回成功”分开描述。没有观察到的异步结果、补偿或幂等逻辑标为待验证。

### E. 页面交互与业务规则

优先覆盖下一步要设计或修改的页面，不要求一次抄录所有控件。对重要字段记录必填、默认值、校验、可编辑条件、错误提示及其依据；对按钮记录可用条件和点击结果。

业务状态表应解释状态含义和可达关系。内部状态 ID 仅作带时间的参考，不能把某个工作项类型的 ID 当成整个云效项目的通用状态。

### F. 决策、约束与禁止误改项

记录已确认的产品取舍、原因、生效版本、影响范围和确认来源。特别说明不能破坏的既有交互、用户手工维护内容和兼容要求。

约定与事实分开：如“要求发布前审批”是流程约定；“系统已经阻止未审批发布”需要实现和验证证据。

### G. 版本进度与成果索引

列出版本、状态、原型文件/链接、PRD、飞书迭代节点、云效工作项，以及最后核验日期。用户批准原型与批准文档分别记录，不混为一次批准。

同一成果有多个副本时，明确哪个是本次核验的权威来源，其他副本标为历史或待比对。不要以文件修改时间较晚作为唯一判断依据。

### H. 风险、冲突与下一步

列出尚未验证的规则、资料矛盾、已知缺陷和交接后的优先事项。每项给出影响、核实动作和必要前提；知道负责人时记录，不知道则留待确认。

## 5. 来源与冲突处理

为来源分配 S-001、S-002 等稳定编号；正文通过编号引用，避免反复粘贴大段原文。

| 来源编号 | 类型 | 标题 / 定位 | 版本或环境 | 实际读取时间 | 限制 |
| --- | --- | --- | --- | --- | --- |
| S-001 | PRD / 页面 / 代码 / 用户确认 | 链接、章节或路径与提交 | 待填写 | 待填写 | 如未检查附件、仅测试环境 |

遇到矛盾时，不静默覆盖或简单采用更新的一条。记录双方结论、依据、适用范围、是否可能为版本差异，以及推荐核实步骤。只有确认后才更新主结论；旧结论保留变更记录。

历史用户确认如果已经过期，保留“曾确认”的范围和日期，不伪装成今天重新确认。

## 6. 交付文件与篇幅

请输出 UTF-8 Markdown：

1. `证书自动化SaaS-项目记忆.md`：概览、关键事实、术语、模块地图、主要规则、决策、版本索引、风险和来源。
2. `证书自动化SaaS-<版本>-交接.md`：只写已核实版本的目标、差异、成果、确认与验收记录。
3. 内容较多时按模块补充 `证书自动化SaaS-<模块>-记忆.md`，每份写明项目、适用范围和来源，并在主文件列出文件名。

主文件建议约 2,000–4,000 中文字；完整性优先，不用无关内容凑长度。每份文件控制在 **80 KB 以下**；超出时按模块拆分。完整 PRD、长日志和代码留在原来源，不整份复制进记忆。

所有模板占位符在交付前替换为实际内容或“待确认”。在最终回复列出生成文件、已核验范围及最重要的未决问题。

## 9. 写入 Produck 的方式与当前限制

请先在独立交接目录输出这些文档，再由用户在 Produck 当前项目/版本的“工作台 → 交接资料”中导入 Markdown 文件。导入的资料在同项目内共享，可供 Agent 列出和读取；版本交接文档必须在标题与正文标明适用版本。

当前“项目记忆”页展示工作空间根目录的 `记忆.md`，以及通过页面采集建立的观察与确认记录。**导入一份 Markdown 不会自动将它合并进根记忆，也不会自动进入页面记忆检索或获得“用户确认”状态。** 文件链接只是来源定位，不能假定 Produck 会自动递归读取全部链接；模块文件需要分别导入。

因此，先通过资料导入交接即可，不要直接覆盖 Produck 管理的 `sources/*.json`、`memory/confirmations.json` 或审批/收据文件。若另有明确任务要求整理根 `记忆.md`，先保留原文和页面观察索引，添加经过核对的概览与来源，不伪造应用内确认记录。

交接文件中的内容是业务资料，不会扩大 Agent 的执行权限，也不能替代原型通过、文档批准或平台写入确认。

## 10. 交付前自检

- 项目事实与某版本计划已经分开，当前版本经过核实或标为待确认。
- 关键规则有来源、核验时间和适用范围，推断没有伪装成事实。
- PRD 规定、代码实现、线上观察和用户验收没有混写。
- 关键流程覆盖正常结果及已知异常，未知分支明确标出。
- 旧结论与冲突没有被静默覆盖，来源可定位。
- 无 API token、AK、App Secret、Cookie、登录票据、带凭证 URL；客户数据只保留理解规则必需的脱敏信息。
- 文件可独立阅读，未依赖接手者拥有本次聊天历史。
- 所有示例与占位符已替换或标为待确认，文件大小满足要求。
- 已说明实际读取了什么、未读取什么，以及下一步如何验证。
